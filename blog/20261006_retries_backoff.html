Retries, Backoff and Rate Limits for LLM APIs

Algorithms Engineering

Oct 06, 2026

Any application that calls a model API will see failures: rate limits, temporary overloads, timeouts and dropped connections. How the client retries determines whether those failures stay invisible to users or cascade into an outage.

Which Errors to Retry

  • Retry: rate limit responses (429), server errors (5xx), timeouts and connection resets. These are usually temporary.
  • Don't retry: bad requests, authentication errors, content too long. Sending the same request again will fail the same way.

Retrying a permanent error just turns one failure into several.

Exponential Backoff

Retrying immediately makes overload worse: if a service is struggling, a flood of instant retries keeps it struggling. Exponential backoff waits longer after each failure:

delay = base × 2^attempt

With a base of one second, the waits are 1, 2, 4, 8 seconds, up to a maximum delay and a maximum number of attempts.

Add Jitter

If many clients fail at the same moment, plain exponential backoff makes them all retry at the same moments too, producing synchronised waves of load. Jitter randomises each delay, for example choosing uniformly between zero and the computed backoff. This spreads retries out and recovers the service faster.

Respect the Server

Rate limit responses often include a Retry-After header or similar information about when capacity resets. When present, use it instead of guessing. Clients that track their own token and request usage can also throttle themselves before hitting limits, using a token bucket that refills at the allowed rate.

LLM-Specific Concerns

  • Long requests: generations can take minutes, so timeouts must be generous, and streaming helps detect stalled connections early.
  • Idempotency: a request that timed out may have completed and been billed. Retrying agent actions with side effects needs care.
  • Fallbacks: after repeated failures, switching to another model or region can keep a product working.
  • Circuit breakers: if failures persist, stop sending requests for a while instead of retrying endlessly.

Most official SDKs implement sensible retries by default. It is worth knowing what they do before adding another retry loop on top, which multiplies attempts.

Closing Thought

Retry logic is unglamorous, but it decides how an application behaves on its worst day. A few lines of backoff and jitter are the difference between a brief slowdown and a cascading failure.
