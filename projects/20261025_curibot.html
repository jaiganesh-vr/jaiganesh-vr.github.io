Curibot: A Stateful Conversational AI Agent

AI Agents LangGraph Full Stack

Oct 25, 2026

Curibot is a chat agent that remembers your conversations and the facts you share about yourself, searches the web when a question needs live information, and streams its answers token by token with cited sources.

The goal of this project was to go beyond a simple prompt-and-reply chatbot and build an agent the way it would be built for production: a model that decides for itself when to use tools, state that survives across sessions, streaming that feels smooth, and logs that help debugging without exposing what users say.

It is built with FastAPI, LangGraph, and React, and backed by PostgreSQL.

Highlights

  • Agent loop with LangGraph — The model decides when to call a tool. Tool results flow back into the graph, with a round limit that forces an answer even from models that ignore tool_choice.
  • Live web search with Tavily — Time-sensitive questions are answered from current results with source links. Search output is treated as untrusted content to guard against prompt injection.
  • Long-term memory — Curibot saves lasting facts and preferences (name, role, how you like answers) and uses them in every conversation. You can review and forget them in a Memory panel.
  • Smooth streaming — Replies arrive over Server-Sent Events and are revealed at a steady, adaptive pace as Markdown. A status line shows "Searching the web…" or "Remembering…" while tools run.
  • Stateful by design — Messages persist in PostgreSQL and graph state in a LangGraph checkpointer. Long histories are trimmed to a token budget, while the full transcript is always kept.
  • Observable and privacy-safe — Structured JSON logs with request IDs and a per-turn summary of tools, latency, and tokens, with no message content.
  • Accessible UI — Dark mode, a mobile drawer, keyboard focus management, native dialog modals, and WCAG AA contrast.

Architecture

The system has three parts. A React 19 frontend talks to a FastAPI backend using JWT-authenticated JSON requests and receives replies as a Server-Sent Events stream. Inside the backend, a LangGraph agent alternates between two nodes: call_model, which sends the prompt to a Groq-hosted LLM (gpt-oss-120b), and tools, which runs web search and memory operations. PostgreSQL 17 stores users, conversations, messages, and memories, alongside the LangGraph checkpoints.

One chat turn works like this:

1. The browser posts the message and opens a Server-Sent Events stream.
2. The backend locks the conversation, loads its history, and reuses the LangGraph checkpoint when it matches the saved transcript.
3. call_model receives a fresh system prompt (identity, today's date, tool guidance, the user's memories) plus history trimmed to a token budget.
4. The model answers or calls tools (web_search, save_memory, delete_memory). Results go back to the model, up to a round limit.
5. Tokens stream to the browser as token events and tool use as tool events. The final answer is saved and sent as done.

Tech Stack

• Frontend — React 19, TypeScript, Vite, plain CSS with light/dark design tokens, react-markdown

• Backend — Python 3.13, FastAPI, SQLAlchemy 2, Alembic, Pydantic settings

• AI — LangGraph, LangChain, Groq (gpt-oss-120b), Tavily search

• Data — PostgreSQL 17 with the LangGraph Postgres checkpointer

• Auth — JWT bearer tokens, Argon2 password hashing

• Observability — Structured JSON logging, request IDs, LangSmith (optional)

• Tooling — uv, Ruff, mypy (strict), pytest, ESLint, Vitest, Docker Compose

Getting Started

You need Docker with Docker Compose, a Groq API key, and optionally a Tavily key for web search. Clone the repository, copy .env.example to .env, and set POSTGRES_PASSWORD, a random JWT_SECRET_KEY (32 or more characters), and GROQ_API_KEY. Then start everything:

docker compose up --build

The app runs at localhost:5173 and the API at localhost:8000, with interactive docs at /docs. Database migrations run automatically when the backend starts, so you can register an account and start chatting.

Design Decisions

  • The system prompt is never stored — It is added to the model input on every turn, never written to the checkpoint or database, so editing it applies to every conversation, including old ones.
  • Trim what the model sees, never what is saved — History is cut to a token budget at a user-turn boundary, without separating a tool call from its result. The database and the UI keep everything.
  • A small Tavily tool instead of an SDK — About 60 lines of httpx with no extra dependencies. Outages return a message to the model, so the turn still completes.
  • Force answers without tools — At the round limit the model is called with no tools bound, and this turn's results move into the prompt. Some models still emit a tool call under tool_choice="none", which the provider then rejects.
  • Memory writes share the turn's transaction — If a turn fails, nothing it saved persists. Database access from parallel tool threads is serialized with a lock.
  • Logs carry identifiers, not content — Request, user, and conversation IDs, timings, and token counts only. HTTP and LLM client loggers are pinned to WARNING, so debug logging cannot leak request bodies.

Testing

The project has 171 backend tests and 86 frontend tests, all of which run without network access. Language models, the search API, and HTTP are replaced with scripted fakes. Separate PostgreSQL integration tests cover row locking and checkpoint recovery.

Coverage includes the agent loop and round limit, streaming events, checkpoint consistency, memory isolation between users, the SSE parser, accessibility behaviour, and a test that logs never contain message content.

Conclusion

Building Curibot showed that most of the work in an AI agent lies outside the model call: managing state, deciding what the model should see, handling tools that fail or misbehave, and making the whole system observable without compromising privacy.
