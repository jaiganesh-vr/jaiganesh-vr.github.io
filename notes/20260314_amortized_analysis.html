Amortized Analysis

Algorithms Analysis

Mar 14, 2026

Some data structures have operations that are usually cheap but occasionally expensive. Worst-case analysis per operation gives a misleadingly pessimistic picture. Amortized analysis bounds the average cost per operation over any sequence of operations, without using probability.

The Classic Example: Dynamic Arrays

A dynamic array, like Python's list, stores elements in a fixed-size block. When it fills up, it allocates a block twice as large and copies everything over.

Most appends cost O(1). An append that triggers a resize costs O(n). Is appending therefore O(n)? Only in the worst case for a single operation. Over many appends, the expensive ones are rare.

Amortized cost is a guarantee about sequences, not an average over random inputs.

The Aggregate Method

Count the total cost of n operations and divide by n.

For n appends with doubling, copies happen at sizes 1, 2, 4, 8, and so on up to n. The total copying is less than 2n, plus n for the appends themselves. So the total is under 3n, and each append costs O(1) amortized.

The Accounting Method

Charge each operation a fixed fee, possibly more than its actual cost, and store the surplus as credit on the data structure. Expensive operations spend that credit.

For dynamic arrays, charge 3 units per append: 1 pays for the insertion, and 2 are saved. When the array doubles, the elements added since the last resize have saved enough credit to pay for copying themselves and the older elements. The credit never goes negative, so 3 per operation is a valid bound.

The Potential Method

Define a potential function Φ on the state of the data structure, representing stored work. The amortized cost of an operation is its actual cost plus the change in potential:

amortized cost = actual cost + Φ(after) − Φ(before)

As long as the potential never drops below its starting value, the total amortized cost bounds the total actual cost. For dynamic arrays, Φ = 2·(number of elements) − (capacity) works neatly: it rises with each cheap append and falls sharply at each resize, paying for the copy.

Another Example: A Binary Counter

Incrementing a binary counter can flip many bits, for example 0111 to 1000. But bit 0 flips every time, bit 1 every second time, bit 2 every fourth time. Over n increments the total number of flips is under 2n, so each increment costs O(1) amortized.

Where It Matters

Amortized bounds explain the efficiency of hash table resizing, union-find with path compression, splay trees and Fibonacci heaps. They are not suitable when every single operation must be fast, as in hard real-time systems.

Closing Thought

Amortized analysis captures a common pattern in data structures: occasional expensive work that pays for itself by making many later operations cheap.
